Use cases

Four ways it gets used

Ad hoc business questions

Answer questions like “how many orders came in this week” or “which customers haven’t ordered in 90 days” on the spot, in a meeting or a Slack thread, without opening a BI tool or writing a query by hand.

Customer and order lookups

Support staff can pull up a customer’s order history or check a product’s stock in seconds, using the same words a customer would use on a call.

Exploring a new or unfamiliar database

Because schema retrieval only surfaces the tables relevant to a given question, a newcomer can ask real questions productively before they’ve memorized table names and relationships.

Follow-up, conversational analysis

Conversation history is stored per session, so a follow-up question like “now break that down by region” carries the context of what was asked before, without repeating it.

In practice

Example interactions

Which customers are from California?

SELECT * FROM customers WHERE state = 'CA' LIMIT 200

There are 3 customers from California: Maria Chen, David Park, and Lena Osei.

What were our 5 best-selling products last quarter?

SELECT p.name, SUM(oi.quantity) AS units_sold FROM order_items oi JOIN products p ON p.id = oi.product_id JOIN orders o ON o.id = oi.order_id WHERE o.created_at >= NOW() - INTERVAL '90 days' GROUP BY p.name ORDER BY units_sold DESC LIMIT 5

The top 5 products by units sold were the Wireless Mouse, Desk Lamp, Notebook Set, Water Bottle, and Phone Stand.

What’s the average rating for the Wireless Mouse?

SELECT AVG(rating) FROM reviews r JOIN products p ON p.id = r.product_id WHERE p.name = 'Wireless Mouse'

The Wireless Mouse has an average rating of 4.3 out of 5.

Built in

Safeguards

  • Read-only by construction. Every query runs inside a Postgres transaction explicitly set to read-only, so even if a write slipped past validation, the database itself refuses it.
  • Statement validation. Generated SQL is rejected before it runs if it isn’t a single SELECT statement, contains write or DDL keywords, or stacks multiple statements.
  • Timeouts and row limits. A statement timeout and an automatic row limit prevent a runaway or overly broad query from tying up the database.
  • Grounded answers. The natural-language answer comes from a second LLM call over the real query results, not from the model guessing at what the data probably looks like.
