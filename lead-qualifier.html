Case study

Lead Qualifier

A hybrid rules + RAG-grounded LLM system that scores inbound HubSpot leads in real time. Architected, built, tested, and deployed end-to-end, solo.

Live API docs View source

The problem

Manual triage doesn’t scale

Inbound leads arrive faster than a sales team can read them. In a CRM list view, a generic form fill and a VP-level buyer with a live budget look identical. Telling them apart means manually opening each record and checking it against the company’s ICP and playbook. That triage is slow, inconsistent between reps, and the leads that most need a fast response are the ones most likely to sit in the queue.

The build

Rules and retrieval-grounded LLM, in one pipeline

A HubSpot webhook fires on every contact update. From there, a deterministic rules engine and an LLM call combine into one score and tier. The result is written straight back into the CRM. The LLM call is grounded via retrieval-augmented generation in the company’s own ICP, sales playbook, and past-deal notes. It reasons from real precedent, not a generic prompt.

HubSpot webhook→ Rules engine→ RAG + LLM scoring→ Write-back + alert
  • Hot → Slack alert
  • Warm → nurture queue
  • Cold → no action

My role

Designed, built, and shipped solo

  • Designed the system in hexagonal (ports-and-adapters) architecture, so the scoring logic stays independently testable from HubSpot, OpenAI, Postgres, and Slack.
  • Built the RAG pipeline: knowledge-base ingestion, chunking, embedding, and pgvector similarity search grounding every LLM call in real ICP and deal context.
  • Wrote a full test suite: unit, adapter, and an LLM eval harness scored against a hand-labeled golden dataset.
  • Set up Alembic migrations and a Dockerized local environment.
  • Stood up a gated CI/CD pipeline: GitHub Actions runs lint, type-check, and tests, and only a green build triggers deployment to FastAPI Cloud.
